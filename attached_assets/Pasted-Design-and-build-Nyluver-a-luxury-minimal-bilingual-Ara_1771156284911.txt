Design and build Nyluver, a luxury-minimal bilingual (Arabic/English) gifting & florist mobile app for iOS/Android with an Admin Panel. The UI layout and navigation patterns must match Floward’s app closely (category layout, product listing, PDP structure, cart/checkout flow, order tracking pages), but use Nyluver’s own colors/typography. Build for one-city launch with a clean path to multi-city expansion.

0) Core operating model

Owned fulfillment only: Nyluver operates central warehouses (no vendor marketplace at launch).

Own delivery fleet: drivers are internal. Delivery dispatch is manual via admin panel.

WhatsApp-first delivery coordination: recipient contact and address collection occurs via WhatsApp (inside operational workflow).

Anonymous gifting only: recipient never sees sender identity. Only platform/admin can see sender.

1) Platforms, architecture, stack choice

Pick the most suitable stack for fast iteration + strong UI parity + maintainability:

Mobile: Flutter (preferred) or React Native. Choose one and justify internally by speed, UI parity, bilingual RTL support, performance.

Backend: Node.js (NestJS) or Laravel.

DB: PostgreSQL.

Cache/queue: Redis + background jobs.

Storage: S3-compatible object storage for product images and delivery evidence.

Notifications: SMS gateway + push notifications.

Payments: bank card gateway + PayPal.

Analytics: event tracking (funnel, slot fill rate, delivery SLA).

2) Roles and access

Only these roles exist at launch:

Customer (Sender)

Admin (Operations + Catalog + Pricing + Dispatch + Support)

No separate driver app at launch. Drivers receive tasks via internal ops method (admin-driven), but the system must model drivers for future expansion.

3) Key differentiators and constraints

Differentiators: price, luxury, speed, personalization.

Exact-match photos: what the customer sees must be what gets delivered. No substitutions allowed.

No refunds policy. Implement replacement/escalation rules without refunding (define outcomes: remake, redelivery, store credit optional only if admin enables later).

Limited delivery slots: strict capacity control.

4) Localization and language

Bilingual equal: Arabic + English across the entire app and admin panel.

Full RTL support for Arabic.

All content fields (product name/description, categories, moods/occasions, banners) must support EN+AR.

5) Geography, cities, currency, VAT

Launch: one city, expand to multiple cities later.

Currency logic:

If paying by local bank card → charge in LYD.

If paying by PayPal → charge in USD.

Pricing/VAT must be configurable from Admin Panel:

VAT enable/disable per city/country

VAT % value

Price display inclusive/exclusive flag

FX rate handling (manual admin-set rate; no external dependency required at launch)

6) Catalog structure and merchandising

Catalog includes:

Flowers and Gifts (gifts start small-scale)

Collections:

By Occasion (Birthday, Anniversary, Congratulations, Apology, etc.)

By Mood (Luxury, Romantic, Minimal, Warm, Elegant, etc.)

Add-ons: all (card message, balloons, chocolates, teddy, premium wrapping tiers, ribbons, etc.)

Product media: multiple images, one primary. Enforce “exact match” tagging.

Inventory approach (must support both until decision is finalized):

Mode A: Stock-based per SKU (central warehouse inventory counts)

Mode B: Daily quota per SKU/collection
Admin can select mode globally and per city.

7) Checkout rules (modified Floward-like journey)

Collect:

Recipient name

Recipient WhatsApp-linked phone number (required)

Address optional (can be provided by sender or collected later from recipient)

Delivery slot selection (see slots below)

Card message (typed only at launch)
Anonymous gifting:

UI must never reveal sender identity to recipient.

Receipt, order tracking, and admin view show sender identity only internally.

Payment:

Only bank card or PayPal

Pay at checkout always

Fraud controls required.

8) Delivery slots and capacity engine

Each day has 3 slots:

10:00–13:00

13:00–18:00

18:00–21:00

Capacity rules:

Default: 50 orders per slot per day (admin editable).

Once slot capacity is reached, slot becomes unavailable in app.

Slot capacity is per city (and optionally per warehouse if multi-warehouse later).

Express delivery:

Standard SLA: 3–4 hours

Express option: extra fee, priority handling

Express availability can be disabled when near capacity.

9) Recipient coordination mechanism (WhatsApp-first)

After payment, order status becomes “Awaiting Recipient Confirmation”.
Operations must:

Contact recipient on WhatsApp to:

confirm acceptance of gift

collect delivery address (if missing)

validate delivery time window (slot)
Rules:

If recipient declines → order becomes “Declined by Recipient” with admin outcome rules (hold, reschedule, convert to store credit if enabled later; no refund).

If recipient doesn’t respond → escalation states and timers:

T+15m reminder

T+60m escalation to admin call

Slot cutoff handling

Implement WhatsApp action helpers:

Tap-to-open WhatsApp with prefilled templates (AR/EN)

Conversation log field in admin (manual notes + timestamps)

Store consent/acceptance outcome
